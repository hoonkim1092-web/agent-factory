# 8인 네트워크 플레이 포커 게임 — 실제 작동 시나리오 시뮬레이션

**작성:** Manus AI  
**기준 규칙:** WSOP(World Series of Poker) 공식 규정 및 Poker TDA 2024 규칙 [1] [2]

---

## 1. 시스템 아키텍처 설계

### 1.1 설계 원칙

본 게임은 **권위 서버(Authoritative Server) 모델**을 채택합니다. 게임의 모든 로직과 상태 판정은 서버에서만 이루어지며, 클라이언트는 서버로부터 전달받은 상태를 화면에 렌더링하고 사용자의 입력을 서버로 전달하는 **뷰어(Viewer)** 역할만 수행합니다. 이 구조는 클라이언트 측의 데이터 조작이나 치팅을 원천적으로 차단합니다.

### 1.2 기술 스택

| 구분 | 기술 | 역할 |
| :--- | :--- | :--- |
| **클라이언트** | HTML5, CSS3, JavaScript (React/Vue.js) | 반응형 UI 렌더링, 사용자 입력 처리 |
| **클라이언트 렌더링** | Canvas / WebGL | 카드 딜링, 칩 이동 애니메이션 |
| **서버 런타임** | Node.js | 게임 로직 엔진, 상태 관리 |
| **실시간 통신** | WebSocket (Socket.io) | 서버-클라이언트 양방향 실시간 통신 |
| **게임 프레임워크** | Colyseus (선택 사항) | 멀티플레이어 룸 및 상태 동기화 |
| **영구 데이터베이스** | MySQL / PostgreSQL | 사용자 계정, 자산, 전적 기록 |
| **세션 관리** | Redis | 실시간 게임 세션 및 상태 캐싱 |

### 1.3 서버-클라이언트 통신 흐름

서버와 클라이언트는 WebSocket을 통해 JSON 형식의 메시지를 주고받습니다. 클라이언트는 서버에 액션 요청을 보내고, 서버는 해당 요청을 검증한 뒤 변경된 게임 상태를 모든 클라이언트에 브로드캐스트합니다.

```
[클라이언트 P1]  ─── { action: "raise", amount: 300 } ──→  [게임 서버]
[게임 서버]      ─── { type: "STATE_UPDATE", pot: 950, ... } ──→  [모든 클라이언트]
```

서버는 클라이언트의 요청이 규칙에 어긋나는 경우(예: 보유 칩 초과 배팅, 턴이 아닌 플레이어의 액션 등) 즉시 거부하고 오류 메시지를 해당 클라이언트에만 전송합니다.

## 2. 게임 규칙 및 초기 설정

### 2.1 기본 게임 설정

게임은 세계 표준 텍사스 홀덤 노 리밋(No-Limit Texas Hold'em) 규칙을 따릅니다. [1] [2] 표준 52장 덱을 사용하며, 조커는 포함하지 않습니다.

| 항목 | 설정값 |
| :--- | :--- |
| **참여 인원** | 최대 8명 (최소 2명 이상 시 게임 시작 가능) |
| **초기 자산 (Buy-in)** | 10,000 칩 |
| **스몰 블라인드 (SB)** | 50 칩 |
| **빅 블라인드 (BB)** | 100 칩 |
| **블라인드 증가 주기** | 20분마다 2배 증가 (토너먼트 모드 적용 시) |
| **액션 타이머** | 플레이어당 15초 (시간 초과 시 자동 폴드) |
| **게임 방식** | No-Limit (최대 배팅 제한 없음, 올인 가능) |

### 2.2 포커 족보 (높은 순서)

| 순위 | 족보 | 설명 |
| :---: | :--- | :--- |
| 1 | **로얄 스트레이트 플러시** | 같은 무늬의 A, K, Q, J, 10 |
| 2 | **스트레이트 플러시** | 같은 무늬의 연속된 5장 |
| 3 | **포 오브 어 카인드** | 같은 숫자 4장 |
| 4 | **풀 하우스** | 같은 숫자 3장 + 같은 숫자 2장 |
| 5 | **플러시** | 같은 무늬 5장 |
| 6 | **스트레이트** | 연속된 숫자 5장 |
| 7 | **쓰리 오브 어 카인드** | 같은 숫자 3장 |
| 8 | **투 페어** | 같은 숫자 2장 + 같은 숫자 2장 |
| 9 | **원 페어** | 같은 숫자 2장 |
| 10 | **하이 카드** | 위 조합 없음, 가장 높은 카드 |

### 2.3 배팅 규칙 (No-Limit)

플레이어는 자신의 턴에 다음 액션 중 하나를 선택할 수 있습니다.

| 액션 | 조건 | 설명 |
| :--- | :--- | :--- |
| **폴드 (Fold)** | 언제나 가능 | 패를 버리고 해당 라운드 포기 |
| **체크 (Check)** | 이전 배팅이 없을 때 | 배팅 없이 다음 플레이어에게 턴 넘김 |
| **콜 (Call)** | 이전 배팅이 있을 때 | 이전 배팅액과 동일한 금액 지불 |
| **배팅 (Bet)** | 이전 배팅이 없을 때 | 최소 BB(100칩) 이상 배팅 |
| **레이즈 (Raise)** | 이전 배팅이 있을 때 | 이전 배팅액의 2배 이상으로 증액 |
| **올인 (All-in)** | 언제나 가능 | 보유한 모든 칩을 배팅 |

올인 발생 시 서버는 자동으로 **메인 팟(Main Pot)**과 **사이드 팟(Side Pot)**을 분리하여 계산합니다. 올인 플레이어는 메인 팟에만 관여하며, 나머지 플레이어들 간의 추가 배팅은 사이드 팟으로 별도 관리됩니다.

## 3. 실제 작동 시나리오 시뮬레이션

### 3.1 시나리오 전제 조건

다음 시나리오는 8명의 플레이어가 게임에 참여하는 한 라운드의 전체 흐름을 서버와 클라이언트 간의 실제 통신 메시지와 함께 상세히 시뮬레이션합니다.

| 플레이어 | 초기 칩 | 포지션 |
| :--- | :---: | :--- |
| P1 | 10,000 | 스몰 블라인드 (SB) |
| P2 | 10,000 | 빅 블라인드 (BB) |
| P3 | 10,000 | UTG (Under the Gun) |
| P4 | 10,000 | UTG+1 |
| P5 | 10,000 | 미들 포지션 |
| P6 | 10,000 | 미들 포지션 |
| P7 | 10,000 | 컷오프 (CO) |
| P8 | 10,000 | 딜러 버튼 (BTN) |

---

### 3.2 Phase 1 — 게임 시작 및 블라인드 지불

8명의 플레이어가 방에 접속을 완료하면, 서버는 게임 상태를 `STARTING`으로 변경하고 무작위로 P8에게 딜러 버튼을 할당합니다. 이에 따라 P1은 스몰 블라인드(50칩), P2는 빅 블라인드(100칩)를 강제로 지불하며, 총 팟(Pot)은 150칩이 됩니다.

**서버 → 전체 클라이언트 브로드캐스트:**
```json
{
  "type": "GAME_START",
  "button_player": "P8",
  "sb_player": "P1",
  "bb_player": "P2",
  "pot": 150,
  "player_chips": {
    "P1": 9950, "P2": 9900, "P3": 10000,
    "P4": 10000, "P5": 10000, "P6": 10000,
    "P7": 10000, "P8": 10000
  }
}
```

클라이언트는 이 메시지를 수신하여 포지션 마커를 렌더링하고, P1과 P2의 칩이 팟으로 이동하는 애니메이션을 출력합니다.

---

### 3.3 Phase 2 — 프리플랍 (Pre-Flop)

서버는 내부 난수 생성기(RNG, Random Number Generator)를 통해 52장의 덱을 셔플합니다. 이후 각 플레이어에게 홀 카드 2장씩을 개별 세션을 통해 비밀리에 전송합니다.

**서버 → P2에게만 전송 (예시):**
```json
{
  "type": "HOLE_CARDS",
  "cards": ["Js", "Qs"]
}
```

다른 플레이어들의 화면에는 P2의 카드가 뒷면으로만 렌더링됩니다. 서버는 UTG인 P3에게 액션 턴을 부여하고 15초 타이머를 시작합니다.

**프리플랍 배팅 시뮬레이션:**

| 순서 | 플레이어 | 액션 | 금액 | 팟 누적 |
| :---: | :--- | :--- | :---: | :---: |
| 1 | P3 (UTG) | 폴드 | - | 150 |
| 2 | P4 | 콜 | 100 | 250 |
| 3 | P5 | 폴드 | - | 250 |
| 4 | P6 | 폴드 | - | 250 |
| 5 | P7 | 폴드 | - | 250 |
| 6 | P8 (BTN) | **레이즈** | 300 | 550 |
| 7 | P1 (SB) | 폴드 | - | 550 |
| 8 | P2 (BB) | 콜 | +200 | 750 |
| 9 | P4 | 콜 | +200 | **950** |

P3가 서버로 `{"action": "fold"}`를 전송하면, 서버는 이를 검증하고 수락한 뒤 P3의 상태를 `FOLDED`로 변경합니다. P8이 300칩으로 레이즈를 선언하자, P1(SB)은 폴드하고 P2(BB)는 추가 200칩을 지불하여 콜합니다. P4도 추가 200칩을 지불하여 콜을 완료합니다. 프리플랍이 종료된 후 총 팟은 950칩이 됩니다.

**서버 → 전체 클라이언트 브로드캐스트 (프리플랍 종료):**
```json
{
  "type": "PREFLOP_END",
  "pot": 950,
  "active_players": ["P2", "P4", "P8"],
  "player_chips": {
    "P1": 9950, "P2": 9700, "P3": 10000,
    "P4": 9700, "P5": 10000, "P6": 10000,
    "P7": 10000, "P8": 9700
  }
}
```

---

### 3.4 Phase 3 — 플랍 (Flop)

서버는 덱에서 번 카드(Burn Card) 1장을 제거한 뒤, 커뮤니티 카드 3장을 공개합니다.

**공개된 플랍 카드:** ♠A (As), ♥K (Kh), ♦7 (7d)

**서버 → 전체 클라이언트 브로드캐스트:**
```json
{
  "type": "FLOP",
  "community_cards": ["As", "Kh", "7d"],
  "pot": 950,
  "action_player": "P2"
}
```

SB인 P1이 폴드했으므로, 남아 있는 플레이어 중 가장 먼저 버튼 왼쪽에 위치한 P2부터 액션이 시작됩니다.

**플랍 배팅 시뮬레이션:**

| 순서 | 플레이어 | 액션 | 금액 | 팟 누적 |
| :---: | :--- | :--- | :---: | :---: |
| 1 | P2 | 체크 | - | 950 |
| 2 | P4 | 체크 | - | 950 |
| 3 | P8 (BTN) | **배팅** | 500 | 1,450 |
| 4 | P2 | 콜 | 500 | 1,950 |
| 5 | P4 | 폴드 | - | **1,950** |

P8이 500칩을 배팅하자 P2는 콜을 선언하고 P4는 폴드합니다. 플랍 라운드가 종료되며 팟은 1,950칩으로 증가하고, 생존자는 P2와 P8 두 명만 남습니다.

---

### 3.5 Phase 4 — 턴 (Turn)

서버는 번 카드 1장을 제거한 뒤, 4번째 커뮤니티 카드를 공개합니다.

**공개된 턴 카드:** ♣2 (2c)

**서버 → 전체 클라이언트 브로드캐스트:**
```json
{
  "type": "TURN",
  "community_cards": ["As", "Kh", "7d", "2c"],
  "pot": 1950,
  "action_player": "P2"
}
```

**턴 배팅 시뮬레이션:**

| 순서 | 플레이어 | 액션 | 금액 | 팟 누적 |
| :---: | :--- | :--- | :---: | :---: |
| 1 | P2 | 체크 | - | 1,950 |
| 2 | P8 | 체크 | - | **1,950** |

P2와 P8 모두 체크를 선언하며 팟의 변동 없이 1,950칩을 유지합니다.

---

### 3.6 Phase 5 — 리버 (River)

서버는 번 카드 1장을 제거한 뒤, 마지막 5번째 커뮤니티 카드를 공개합니다.

**공개된 리버 카드:** ♠10 (Ts)

**서버 → 전체 클라이언트 브로드캐스트:**
```json
{
  "type": "RIVER",
  "community_cards": ["As", "Kh", "7d", "2c", "Ts"],
  "pot": 1950,
  "action_player": "P2"
}
```

이 시점에서 P2는 자신의 홀 카드(♠J, ♠Q)와 커뮤니티 카드(♠A, ♥K, ♦7, ♣2, ♠10)를 조합하여 ♠10, ♠J, ♠Q, ♠K, ♠A의 **로얄 스트레이트 플러시**를 완성했음을 인지합니다.

**리버 배팅 시뮬레이션:**

| 순서 | 플레이어 | 액션 | 금액 | 팟 누적 |
| :---: | :--- | :--- | :---: | :---: |
| 1 | P2 | **올인** | 9,200 | 11,150 |
| 2 | P8 | 콜 | 9,200 | **20,350** |

P2가 남은 모든 칩(9,200칩)을 올인합니다. P8은 이에 콜을 선언합니다. 리버 라운드가 종료되며 최종 팟은 20,350칩이 됩니다.

> **참고:** P2의 초기 칩 10,000에서 프리플랍(300), 플랍(500)을 지불했으므로 리버 시점의 보유 칩은 9,200칩입니다.

---

### 3.7 Phase 6 — 쇼다운 (Showdown) 및 결과 판정

리버 배팅이 종료되면 서버는 모든 활성 플레이어의 홀 카드를 전체 클라이언트에 공개하도록 요청합니다. 서버의 족보 판정 엔진이 각 플레이어의 7장(홀 카드 2장 + 커뮤니티 카드 5장) 중 최고의 5장 조합을 계산합니다.

| 플레이어 | 홀 카드 | 최고 5장 조합 | 족보 |
| :--- | :--- | :--- | :--- |
| **P2** | ♠J, ♠Q | ♠10, ♠J, ♠Q, ♠K, ♠A | **로얄 스트레이트 플러시** |
| P8 | ♥A, ♣A | ♥A, ♣A, ♠A, ♥K, ♠10 | 쓰리 오브 어 카인드 (A) |

서버는 P2의 로얄 스트레이트 플러시가 P8의 쓰리 오브 어 카인드보다 높음을 판정하고 P2를 승자로 결정합니다.

**서버 → 전체 클라이언트 브로드캐스트:**
```json
{
  "type": "SHOWDOWN",
  "winner": "P2",
  "pot_awarded": 20350,
  "hands": {
    "P2": { "cards": ["Js", "Qs"], "rank": "Royal Straight Flush" },
    "P8": { "cards": ["Ah", "Ac"], "rank": "Three of a Kind" }
  },
  "final_chips": {
    "P1": 9950, "P2": 20350, "P3": 10000,
    "P4": 9700, "P5": 10000, "P6": 10000,
    "P7": 10000, "P8": 650
  }
}
```

클라이언트는 이 메시지를 수신하여 P2의 승리 이펙트를 출력하고, 팟의 칩이 P2에게 이동하는 애니메이션을 렌더링합니다. 약 3~5초의 대기 후 서버는 딜러 버튼을 P1으로 이동시키고 다음 라운드 준비 상태로 전환합니다.

## 4. 클라이언트 화면 구성 (앱웹 반응형 설계)

클라이언트는 HTML5 기반의 단일 페이지 애플리케이션(SPA)으로 개발되며, CSS 미디어 쿼리와 Flexbox/Grid 레이아웃을 활용하여 모바일, 태블릿, PC 환경에 모두 최적화됩니다.

| 화면 영역 | 구성 요소 | 설명 |
| :--- | :--- | :--- |
| **중앙 테이블** | 커뮤니티 카드, 팟 금액 표시 | Canvas로 렌더링, 카드 딜링 애니메이션 포함 |
| **플레이어 슬롯** | 아바타, 닉네임, 보유 칩, 카드 뒷면 | 8개의 좌석이 타원형으로 배치 |
| **내 카드 영역** | 홀 카드 2장 (본인만 확인 가능) | 화면 하단에 크게 표시 |
| **배팅 컨트롤** | 폴드, 체크/콜, 레이즈, 올인 버튼 | 내 턴에만 활성화, 슬라이더로 금액 조절 |
| **채팅 창** | 텍스트 채팅 | 선택 사항, 우측 패널에 배치 |
| **게임 정보** | 블라인드 레벨, 타이머, 핸드 히스토리 | 상단 헤더에 표시 |

모바일 환경에서는 배팅 컨트롤이 화면 하단에 고정 배치되어 엄지손가락으로 조작하기 편리하도록 설계됩니다. 태블릿 및 PC 환경에서는 더 넓은 화면을 활용하여 게임 정보와 채팅 창이 함께 표시됩니다.

---

## 5. 보안 및 공정성 보장 메커니즘

게임의 공정성과 보안을 위해 서버 측에서 다음과 같은 메커니즘이 적용됩니다.

서버는 **암호학적으로 안전한 난수 생성기(CSPRNG)**를 사용하여 덱을 셔플합니다. 이를 통해 카드 배분의 예측 불가능성을 보장합니다. 또한 각 플레이어의 홀 카드는 해당 플레이어의 세션에만 전송되며, 다른 클라이언트에는 절대 노출되지 않습니다. 서버는 모든 클라이언트 요청을 수신할 때마다 해당 플레이어의 턴 여부, 보유 칩 충분 여부, 최소 배팅액 준수 여부를 검증하여 비정상적인 요청을 즉시 거부합니다. 액션 타이머가 만료되면 서버가 자동으로 해당 플레이어를 폴드 처리하여 게임 진행이 지연되지 않도록 합니다.

---

## 6. 구현 시 핵심 고려 사항

실제 개발 시 가장 중요하게 다루어야 할 기술적 과제는 **WebSocket 연결 안정성**입니다. 네트워크 불안정으로 인해 클라이언트의 연결이 끊어지는 경우, 서버는 해당 플레이어의 세션 상태를 Redis에 보존하고 재접속 시 현재 게임 상태를 복원하여 전송해야 합니다. 또한 **동시성 처리(Concurrency)**에 주의해야 합니다. 여러 플레이어가 동시에 액션을 전송하는 경우, 서버는 큐(Queue) 방식으로 요청을 순차적으로 처리하여 레이스 컨디션(Race Condition)이 발생하지 않도록 해야 합니다. 마지막으로 **사이드 팟 계산 로직**은 올인이 중첩될 경우 매우 복잡해지므로, 이를 처리하는 별도의 팟 계산 모듈을 서버에 구현하는 것이 권장됩니다.
