## Rule

외부 에이전트(codex, gemini, 외부 리뷰어)의 의견을 평가할 때, **"균형 잡힌 분석" 인상을 주려고 어줍짢은 흠/과장 라벨을 끼우지 말 것**. 비판은 코드·사실 grep 근거로만. 동의 사항은 솔직히 동의.

**Why**: 2026-05-04 codex_my_의견.md 분석에서, codex 권고를 평가하며 "정확한 부분 / 과장된 부분"으로 나눠 적음. 사용자가 "왜 과장이라는 거지?"라 추궁 → 다시 보니 3개 "과장" 항목이 모두 codex 글에 없었음. "5개 신규 모듈 신설 뉘앙스"는 codex가 명시적으로 "추가가 아닌 배선 강도"라 한 것을 내가 항목명만 보고 오독한 것. "prepare() 거대 게이트"는 codex가 위치만 지정한 것을 내가 거대함으로 오독. "포커 특화"는 codex 자신이 CoverageGate 매니페스트로 일반화 메커니즘을 제시했음에도 모순으로 라벨한 것. 셋 다 균형 인상을 위한 가짜 흠. Sycophancy의 거울상.

**How to apply**:
- 외부 의견 분석 시 "정확한 부분 / 과장된 부분" 같은 균형 양식을 default로 쓰지 말 것
- 비판은 반드시 grep + 코드 발췌 + 외부 글 인용 3박자로
- 항목명에서 "신규 모듈처럼 들리네" 같은 1차 인상으로 비판 라벨 붙이지 말 것 — 글 전체 맥락(도입부·결론) 다시 확인
- 동의가 정답이면 동의가 정답. "그래도 흠 한두 개는 있어야지"는 sycophancy
- Karpathy "Think Before Coding §1": 가정 명시 — 동의 사항인지, 진짜 흠인지, 본인 오독인지를 먼저 확인
