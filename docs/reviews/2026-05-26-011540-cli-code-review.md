### Findings

1. [Medium] Forced UTF-8 replacement can corrupt Git context injected into prompts
   - File: `core/providers/cli.py:620`
   - Code: `subprocess.run(["git", "log", "-5", "--oneline"], cwd=repo_root, capture_output=True, text=True, encoding="utf-8", errors="replace", timeout=3, check=False)`
   - Issue: Git output encoding can vary on Windows or by Git config. `errors="replace"` prevents crashes, but silently injects replacement characters into `[Git State]`, so commit subjects, branch names, or status lines with non-UTF-8 bytes can be corrupted before reaching Claude/Gemini/Codex.
   - Suggestion: Force Git itself to emit UTF-8, e.g. `git -c i18n.logOutputEncoding=UTF-8 ...`, or capture bytes and decode with a fallback path. Add a regression test for non-ASCII commit/status output.

2. [Info] Changed subprocess calls do not introduce shell injection
   - File: `core/providers/cli.py:605`
   - Code: `subprocess.run(["git", "rev-parse", "--short", "HEAD"], cwd=repo_root, capture_output=True, text=True, encoding="utf-8", errors="replace", timeout=3, check=False)`
   - Issue: No security defect found here. The command remains list-form with `shell=False` default, and `repo_root` comes from `_detect_repo_root()` rather than shell interpolation.
   - Suggestion: Keep this pattern; do not convert these calls to string commands.

3. [Info] Progress text change appears API-safe for in-repo callers
   - File: `core/providers/cli.py:906`
   - Code: `print(f"  [{display_name}] done ({mins}m {secs}s)", flush=True)`
   - Issue: No in-repo caller found parsing the old Korean/emoji progress strings. Callers use the returned dict from `execute_cli_chat()`, e.g. `core/agent_runner.py:592`, `core/cross_verification.py:200`, and `model_utils.py:755`.
   - Suggestion: If external log parsers depend on these strings, document the new stable format or emit structured events separately.
