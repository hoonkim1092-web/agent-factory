## Critic Review

### Verdict: BLOCK

### Findings

1. [Critical] `blast_radius` trigger value does not match current code
   - Section: "`requires_domain_review = True` for `blast_radius == \"system\"`" / "`def require_domain_review(blast_radius: str) -> bool: return blast_radius == \"system\"`"
   - Issue: The real `ChangeImpactProfiler` never emits `"system"`. It emits `"system_wide"` for system-level changes: [core/control/change_impact.py](D:/hoonProJect/worktrees/agent-factory/core/control/change_impact.py:35), [core/control/change_impact.py](D:/hoonProJect/worktrees/agent-factory/core/control/change_impact.py:217). Implementing the design literally makes the Domain Gate never trigger for the intended system-wide changes.
   - Suggestion: Change the design and tests to use `blast_radius == "system_wide"` or introduce a normalization helper with explicit mapping from legacy/design terms to current enum values.

2. [Critical] The proposed `work_kind` / `blast_radius` frontmatter has no real data path
   - Section: "`work_item_generator.py`가 work-item frontmatter에 `work_kind`/`blast_radius` 미리 기재, `ApprovalGate`가 read"
   - Issue: The current project pipeline does not pass `NormalizedRequest` into `generate_work_items()`. `ProjectPipeline.prepare_brief()` only calls `ControlPlaneIntake()._recall_from_memory()` at [core/project_pipeline.py](D:/hoonProJect/worktrees/agent-factory/core/project_pipeline.py:706), not `normalize()`. `generate_work_items()` receives only `workspace`, `slug`, `project_brief`, `role_plan`, `task_board`, `run_id` at [core/work_item_generator.py](D:/hoonProJect/worktrees/agent-factory/core/work_item_generator.py:1072), and the caller passes no `work_kind` or `change_impact` at [core/project_pipeline.py](D:/hoonProJect/worktrees/agent-factory/core/project_pipeline.py:959). The design’s stack diagram claims a route through `ControlPlaneIntake.normalize()`, but that path is not connected to work-item generation.
   - Suggestion: Specify one concrete integration point: either call `ControlPlaneIntake.normalize()` in `ProjectPipeline.prepare_brief()` and inject `project_brief["work_kind"]` / `project_brief["change_impact"]`, or extend `generate_work_items(..., normalized: NormalizedRequest | dict | None)` and update all callers/tests.

3. [High] Frontmatter fail-closed conflicts with migration/backward compatibility
   - Section: "`frontmatter read 시점: ApprovalGate.approve() 진입 직후 ... 누락 시 BlockedExecutionError(\"missing work-item frontmatter: work_kind/blast_radius\")`" and "`기존 work-item은 자동 통과`"
   - Issue: These statements conflict. Existing `approval-gate.md` documents and generated work-item docs do not currently contain `work_kind` / `blast_radius`; `ApprovalGate.initialize()` only writes approval metadata at [core/approval_gate.py](D:/hoonProJect/worktrees/agent-factory/core/approval_gate.py:128), and `_DOC_FILES` tracks document hashes only at [core/approval_gate.py](D:/hoonProJect/worktrees/agent-factory/core/approval_gate.py:80). A hard `BlockedExecutionError` in `approve()` would block old work-items and maintenance flows despite §10 saying existing work-items pass.
   - Suggestion: Make missing frontmatter non-blocking unless an explicit activation flag/version is present, e.g. `domain_gate_version: 1`, or read fallback metadata from `.af_runtime/control/change_impact.json` before failing closed.

4. [High] `domain-review.md` template is not generated by the described code path
   - Section: "`docs/work-items/_template/domain-review.md`" and "`_DOC_FILES에 domain-review.md 추가`"
   - Issue: `generate_work_items()` writes four generated docs and initializes `approval-gate.md`; extra templates are copied only by `_copy_extra_templates()`, which currently copies `verification-report.md`, `change-request.md`, and `bug-fix-spec.md` at [core/work_item_generator.py](D:/hoonProJect/worktrees/agent-factory/core/work_item_generator.py:1087). The design does not say to add `domain-review.md` to this copy set or to generate it directly. Result: required system-wide work-items can be blocked for a missing document without giving users the template in the work-item folder.
   - Suggestion: Add `domain-review.md` to `_copy_extra_templates()` and include a test that a system-wide work-item contains the copied template before approval.

5. [Medium] Verdict parsing is underspecified and fragile
   - Section: "`domain-review.md verdict 검사 (verdict ∈ {PASS, NEEDS_ADR, BLOCK})`" and template checkboxes for `PASS`, `NEEDS_ADR`, `BLOCK`
   - Issue: The design does not define how `ApprovalGate` parses the verdict from markdown checkboxes: multiple checked boxes, zero checked boxes, lowercase text, Korean labels, or stale verdicts are all possible. Current `ApprovalGate._parse()` only parses `approval-gate.md` sections, not external docs: [core/approval_gate.py](D:/hoonProJect/worktrees/agent-factory/core/approval_gate.py:438).
   - Suggestion: Define a strict machine-readable line in `domain-review.md`, e.g. `verdict: PASS`, and fail closed on missing/invalid/multiple verdicts. Add table tests for PASS, NEEDS_ADR, BLOCK, missing, and malformed.

6. [Medium] `skills/systematic_debugging/SKILL.md` alone will not register as an AF skill
   - Section: "`skills/systematic_debugging/SKILL.md` 설계 (AF 자체 형식)" and "`core/skill_loader.py 자동 발견`"
   - Issue: AF’s registry auto-detection is metadata driven. Existing knowledge skills use `meta.yaml` with `content_path: SKILL.md`, e.g. `skills/graphify_guide/meta.yaml`. The registry scans directories and calls metadata conversion at [core/skill_registry.py](D:/hoonProJect/worktrees/agent-factory/core/skill_registry.py:194). Creating only `SKILL.md` may not make the skill discoverable by `core/skill_loader.py`.
   - Suggestion: Specify `skills/systematic_debugging/meta.yaml` with `type/category/status/when_to_use_keywords/content_path: SKILL.md`, and add a registry test asserting the skill appears in `get_global_registry().get_all()`.

### Missing from Design

- Exact enum contract for `blast_radius`: current values are `isolated`, `module`, `cross_module`, `system_wide`.
- Concrete propagation of `work_kind` and `change_impact` from intake to `project_brief` or `generate_work_items()`.
- Migration behavior for existing work-items without frontmatter.
- `target_path` test where docs live outside the AF workspace.
- `domain-review.md` copy/generation path.
- Machine-readable verdict schema and malformed verdict handling.
- `af.spec` impact check for any new Python module such as `core/brainstorm_prompts.py`.

### Positive Observations

- The design correctly rejects direct Superpowers import and external package coupling, which avoids adding a `claude_cli`-specific dependency path.
- Choosing `ApprovalGate` as the enforcement point is directionally consistent with the existing execution-open contract and document snapshot mechanism.
