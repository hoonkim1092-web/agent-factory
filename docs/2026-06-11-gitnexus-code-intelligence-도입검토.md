# GitNexus — 코드 인텔리전스(Graph) 도입 검토

> 작성일: 2026-06-11
> 목적: 코드베이스 구조를 그래프로 이해시키는 도구 GitNexus의 역할·시너지·도입 단계 정리 (회의 논의용)
> ※ 이 문서는 GitNexus만 다룹니다. RAG 논의 맥락은 본 문서 앞/뒤에 별도로 합쳐 주세요.

---

## 0. 한 줄 요약

> **GitNexus = 코드베이스를 "쿼리 가능한 지식 그래프"로 만들어, AI 에이전트(Claude Code, Cursor 등)에게 "이 함수를 고치면 무엇이 깨지는가"를 한 번에 답해주는 도구.**

- npm 패키지: **`gitnexus`** (v1.6.7, 오픈소스)
- 런타임: **Node.js** (Python 버전과 무관 — 설치 장벽 낮음)
- 핵심: 텍스트 검색(grep)·의미 검색(벡터 RAG)이 못 잡는 **코드의 구조적 관계**(import / 호출 / 상속)를 잡는다.

---

## 1. 무슨 문제를 푸는가

AI 코딩 에이전트가 큰 코드베이스에서 겪는 근본 한계:

| 기존 방식 | 잡는 것 | 못 잡는 것 |
|-----------|---------|-----------|
| **grep / IDE 검색** | 텍스트가 어디 있는지 | "이게 누구를 호출하고, 누가 이걸 호출하는지" 관계 |
| **벡터 RAG (임베딩 검색)** | 의미가 비슷한 코드 조각 | 코드의 **구조적 의존 관계** (호출/상속/import) |
| **GitNexus (그래프)** | **구조적 관계 + 영향 범위 + 실행 흐름** | "왜 이렇게 짰는가"(설계 의도 — 이건 사람 문서 영역) |

핵심 차이를 비유로:

> 벡터 RAG는 **"비슷하게 생긴 문장 찾기"** (도서관에서 비슷한 책 추천).
> GitNexus는 **"이 부품을 빼면 어떤 기계가 멈추는지 배선도 추적"** (회로도).
>
> 둘은 경쟁이 아니라 **보완** — 의미 검색 + 구조 검색.

에이전트가 "이 함수 하나 이해하려고 그래프 쿼리를 10번 연쇄"하는 대신, GitNexus는 **미리 계산된 의존 구조**에서 신뢰도 점수가 매겨진 영향 범위를 **단 한 번의 호출로** 반환한다.

---

## 2. 어떻게 동작하는가 (인덱싱 파이프라인)

```
1. 파일 트리 순회
2. Tree-sitter로 AST 파싱      (14개 언어: Python, JS/TS, Java, Go, Rust, C/C++ …)
3. import / 호출 / 상속 관계 해석   → 방향 그래프 구축
4. Leiden 군집화                  → 연관 코드 묶음(모듈/도메인) 자동 발견
5. 실행 흐름(process) 추적
6. 하이브리드 검색 인덱싱          (BM25 키워드 + 시맨틱 벡터 + RRF 융합)
   └ 결과 저장: LadybugDB (로컬 임베디드 그래프 DB, .gitnexus/ 폴더)
```

- 저장은 **repo 로컬** (`.gitnexus/`, gitignore 대상) + 전역 레지스트리(`~/.gitnexus/registry.json`)
- 서버 불필요 — 로컬에서 완결 ("Zero-Server")

---

## 3. 핵심 도구 (총 16개 중 주요 7개)

| 도구 | 하는 일 | 언제 쓰나 |
|------|---------|-----------|
| **`impact`** | **영향 범위(blast radius) 분석** — 깊이별 그룹 + 신뢰도 점수 | "이거 고치면 뭐가 깨지나" |
| **`context`** | 심볼 360° 뷰 — 참조 분류 + 실행 흐름 참여 | "이 함수 주변을 통째로 이해" |
| **`query`** | 프로세스 단위 하이브리드 검색 | 자연어로 코드 찾기 |
| **`detect_changes`** | git diff → 영향받는 실행 흐름 매핑 | "이번 변경의 파급" |
| **`rename`** | 그래프 기반 멀티파일 일괄 리네임 | 안전한 대규모 리네임 |
| **`cypher`** | 원시 그래프 쿼리 (DB 직접 질의) | 고급 커스텀 분석 |
| **`list_repos`** | 인덱싱된 repo 탐색 (멀티 repo) | 여러 프로젝트 관리 |

제공 인터페이스: **CLI** (자동화·스크립트용) + **MCP** (Claude Code/Cursor가 자율 호출) + 선택적 Web UI.

---

## 4. 우리에게 주는 시너지

1. **영향 범위 분석 정밀화** — 변경 파일이 "다른 무엇을 망가뜨리는가"(역방향 의존)를 그래프로 추적. 텍스트 검색·룰 기반 분류로는 불가능.
2. **대규모 코드베이스 임계 돌파** — 파일 수가 수백 개를 넘으면 사람·문서로 의존성 추적이 비현실적. 그래프 쿼리가 보강.
3. **AI 토큰 절감** — 관련 코드를 통째로 LLM에 넣는 대신, 신뢰도순 관련 심볼만 반환 → 컨텍스트 비용 ↓.
4. **벡터 RAG의 빈틈 메우기** — 의미 검색이 놓치는 "정확한 호출/의존 경로"를 보완. (RAG 파이프라인에 그래프 검색 채널을 추가하는 그림)

## 5. ⭐ 도입 단계 (명시적 — 단계별 독립 중단 가능)

> 원칙: **각 단계는 default-off로 시작하고, 측정 후 다음 단계로.** 기존 워크플로를 깨지 않는다.

```
■ Step 0 — PoC : "진짜 되나?" 확인  (15~20분, 비용 0, 코드 0)
  ─ 격리된 임시 폴더에 repo를 복제
  ─ 실행:  npx gitnexus@1.6.7 analyze
  ─ 측정:  ① 인덱싱 소요 시간  ② 그래프 DB 생성 확인  ③ impact 쿼리 1건 정확도
  ─ ⚠️ 주의: analyze가 AGENTS.md / CLAUDE.md / hook 설정을 자동 생성·덮어쓸 수 있음
            → 반드시 격리 폴더에서 먼저. 본 repo 루트 직접 실행 금지.
  ─ 게이트:  품질 OK → Step 1 / 느리거나 부정확 → 여기서 중단

■ Step 1 — Wrapper : 자동화에서 호출 가능하게  (~60줄, default OFF)
  ─ CLI를 감싸는 얇은 wrapper 작성 (impact / detect_changes 호출)
  ─ GitNexus 미설치·미인덱싱 시 조용히 빈 결과 반환 (예외로 죽지 않게)
  ─ 기존 검색·분류 로직은 그대로 — GitNexus는 "추가 신호"이지 대체가 아님

■ Step 2 — 통합 : 실제 워크플로에 연결  (opt-in 환경변수)
  ─ 환경변수 ON일 때만 GitNexus impact 호출
  ─ 기존 판정과 GitNexus 결과를 "안전 방향으로만" 결합 (영향 범위는 넓게 잡되 좁히지 않음)
  ─ 1~2주 운영 후 정확도 비교 (놓친 영향 = false negative 감소 측정)

■ Step 3 — 운영 정책 결정 : 측정 결과로 판단
  ─ 만족 →  default ON 전환 검토
  ─ 불만족 →  opt-in 유지 또는 폐기
  ─ 기존 코드 그래프 도구가 있다면 역할 분리 or 폐기 결정

■ Step 4 (선택) — MCP 사용자 채널 : 사람이 직접 질문
  ─ 자동 흐름은 CLI(subprocess) 유지  ← 통제 보존
  ─ MCP는 "사람이 채팅으로 즉석 질문"용으로만 분리 등록
  ─ 두 채널을 명확히 분리 (자율 호출이 자동 흐름을 건드리지 않게)
```

## 6. 고려사항 / 리스크

| 항목 | 내용 | 대응 |
|------|------|------|
| **MCP 자율 호출** | MCP는 AI가 사용자 모르게 호출 — 비용·통제 이슈 | 자동 흐름은 CLI, MCP는 사용자 채널로 분리 (Step 4) |
| **인덱스 신선도** | 코드 바뀌면 재인덱싱 필요 (`analyze` 재실행) | git hook 또는 주기적 재인덱싱 정책 |
| **PC 간 일관성** | `.gitnexus/` DB는 PC 로컬 (공유 안 됨) | 멀티 PC면 각 PC에서 `analyze` 재실행 |
| **자동 파일 생성** | `analyze`가 기존 AGENTS.md/CLAUDE.md 덮어쓸 위험 | Step 0 격리 테스트로 사전 확인 |
| **언어별 기능 편차** | 14개 언어 지원하나 기능(타입 추론 등)은 언어마다 다름 | 주력 언어(Python/TS) 정확도를 Step 0에서 확인 |

---

## 7. 한눈에 보는 결론

- GitNexus는 **코드 구조 그래프** 도구 — 텍스트 검색·벡터 RAG가 못 잡는 **호출/의존/상속 관계**를 잡는다.
- 벡터 RAG와는 **경쟁이 아니라 보완** (의미 검색 + 구조 검색).
- 도입은 **Step 0 PoC(20분, 비용 0)로 즉시 검증 가능** — Node만 있으면 됨.
- 위험은 주로 **MCP 자율 호출**과 **자동 파일 생성** — 둘 다 "CLI 우선 + 격리 테스트"로 통제 가능.
