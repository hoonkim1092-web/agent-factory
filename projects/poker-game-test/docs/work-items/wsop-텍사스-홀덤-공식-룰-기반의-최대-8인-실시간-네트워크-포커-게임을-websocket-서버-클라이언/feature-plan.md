## Background

텍사스 홀덤은 WSOP(World Series of Poker) 표준으로 전 세계에서 가장 공신력 있는 포커 형식이다. 프리플랍·플랍·턴·리버 4단계 베팅 구조를 채택하며, 핸드 랭킹·킥커 규칙·사이드팟 계산 등 복잡한 게임 로직을 수반한다.

본 프로젝트는 최대 8인이 동시에 참여할 수 있는 실시간 네트워크 포커 게임을 구현한다. 게임 로직 전부를 서버에 집중시키고 클라이언트는 렌더링과 입력 전송 전담 구조(Single Source of Truth)를 채택한다. 별도 앱 설치 없이 모바일·PC·태블릿 브라우저에서 동작해야 하므로 순수 HTML5/CSS3/Vanilla JS 클라이언트가 요구된다.

기존 연구 문서(`project-brief.json`)에 제약사항과 산출물 범위가 이미 정의되어 있으며, 본 계획은 이를 기반으로 구현 순서와 역할 분담을 구체화한다.

---

## Problem Statement

게임 판정 로직이 클라이언트에 분산되면 다음과 같은 신뢰성 문제가 발생한다.

- **핸드 비교 조작**: 클라이언트 메모리 변조를 통한 패 위조 가능
- **사이드팟 계산 오류**: 클라이언트별 독립 계산 시 팟 금액 불일치
- **치팅 취약성**: 패킷 변조·타임아웃 조작·멀티 계정 공모 방어 불가

이를 해결하기 위해 모든 게임 상태 전이를 서버 단일 진실 소스로 집중시키고, 클라이언트는 렌더링과 입력 전송만 담당하는 구조를 채택해야 한다.

---

## Goals

1. WSOP 표준 텍사스 홀덤 룰(프리플랍·플랍·턴·리버 4단계 베팅)을 서버 단독으로 완전 구현한다.
2. WebSocket 전이중 통신 기반으로 최대 8인 동시 실시간 플레이를 지원한다.
3. 별도 앱 설치 없이 모바일·PC·태블릿 브라우저에서 동작하는 HTML5 클라이언트를 제공한다.
4. 핸드 평가(7장 중 최강 5장 조합), 사이드팟 다중 계산, 턴 타임아웃 자동 폴드를 서버가 완전 처리한다.
5. 클라이언트는 서버가 전달한 공개 상태 스냅샷만 렌더링하며 어떠한 게임 판정도 수행하지 않는다.

---

## Non-Goals

- 실제 현금 베팅 또는 결제 시스템 (가상 칩만 사용)
- AI 봇 플레이어 구현
- 채팅 기능
- 토너먼트·리그 구조 (단일 캐시 게임만)
- 세븐카드 스터드·오마하 등 다른 포커 변형 게임
- 계정 영구 저장·로그인 시스템 (세션 내 닉네임만)
- 모바일 네이티브 앱 빌드 (웹앱만)
- 관전자 모드
- 게임 히스토리 저장·통계
- 하프·따당 등 하우스룰 베팅

### 기술 스택

| 레이어 | 기술 |
|--------|------|
| 서버 | Python 3.11, websockets 12.x (asyncio 기반) |
| 게임 루프 | asyncio (턴 타임아웃·비동기 이벤트 루프) |
| 클라이언트 | HTML5 / CSS3 / Vanilla JS ES2022 |
| 레이아웃 | CSS Grid + Flexbox (반응형) |
| 통신 프로토콜 | JSON over WebSocket |

### 핵심 제약사항

| 제약 | 상세 |
|------|------|
| 서버 단독 판정 | 게임 판정(핸드 비교, 팟 계산, 턴 진행) 전부 서버 전담 |
| 클라이언트 순수 웹 | 순수 HTML5/CSS3/Vanilla JS — 앱 설치 불필요 |
| 동시 접속 | 최대 8명, 최소 2명 이상 시 게임 시작 |
| WSOP 룰 | 프리플랍/플랍/턴/리버 4단계 베팅 구조 |
| 초기 자산 | 플레이어당 1,000 chips 고정 지급 |
| 블라인드 | 스몰 10 / 빅 20 고정 |
| 허용 액션 | 폴드·체크·콜·레이즈·올인만 (하우스룰 미지원) |
| 칩 소진 처리 | 즉시 게임 아웃, 사이드팟 자동 계산 |
| 인증 | 세션 내 닉네임만 — 영구 계정·로그인 없음 |
| 통신 | WebSocket 전이중 통신으로 실시간 상태 동기화 |

### 구현 단계 (실행 전략: 병렬)

```
Phase 1 (범위 정의)
  ├── 룰 엔진 인터페이스 정의 (Game Logic Dev)
  ├── WebSocket 서버 인터페이스 정의 (Backend Dev)
  ├── HTML5 클라이언트 인터페이스 정의 (Frontend Dev)
  └── QA 검증 범위 정의 (QA Engineer)

Phase 2 (기능 구현)
  ├── 핸드 평가·팟·사이드팟·턴 진행 구현
  ├── WebSocket 게임 서버 구현
  ├── 로비 UI + 게임 화면 + 베팅 UI 구현
  └── 반응형 레이아웃 구현

Phase 3 (통합 및 핸드오프)
  ├── 서버-클라이언트 이벤트 프로토콜 연결
  └── 역할 간 handoff 메모 작성

Phase 4 (검증 및 마감)
  ├── 핸드 랭킹·사이드팟·타임아웃 단위 검증
  └── 잔여 리스크 및 후속 작업 기록
```

## Risks and Assumptions

### 리스크

| # | 리스크 | 영향도 | 대응 방안 |
|---|--------|--------|-----------|
| R1 | WebSocket 연결 단절 시 게임 상태 복구 로직 부재 | 높음 | 플레이어 탈락 처리 정책 사전 확정 (60초 유예 후 자동 폴드) |
| R2 | 8인 동시 베팅 타임아웃 미처리 | 높음 | 서버 asyncio `wait_for` 기반 턴 자동 폴드 로직 필수 구현 |
| R3 | 사이드팟 다중 계산 버그 | 높음 | 올인 플레이어 조합별 단위 테스트 필수 |
| R4 | 모바일 터치 UI 레이즈 금액 입력 UX 미흡 | 중간 | 터치 친화 슬라이더·버튼 preset 설계 별도 검토 |
| R5 | 핸드 평가기 엣지케이스 오판정 (동률·키커·에이스 하이/로우 스트레이트) | 높음 | 21가지 조합(7C5) 전수 검증 테스트 작성 |

### 가정 사항

- 서버는 단일 Python 프로세스 내에서 asyncio 이벤트 루프를 통해 동시 8개 WebSocket 연결을 처리할 수 있다.
- 클라이언트는 항상 서버가 전달한 상태 스냅샷을 신뢰하며, 별도의 클라이언트 측 상태 검증을 수행하지 않는다.
- 재접속은 지원하지 않는다 (세션 내 게임 한정).
- 초기 칩 및 블라인드는 고정값으로 서버 설정 파일에서 관리된다.

## Approval Request

본 Feature Plan은 다음 사항의 승인을 요청한다.

1. **서버 단독 판정 구조** 확정 — 클라이언트는 렌더링·입력 전송만 담당하며 게임 로직 없음
2. **초기 칩 1,000 chips, 스몰 블라인드 10 / 빅 블라인드 20** 고정값 확정
3. **재접속 불가 정책** 확정 — 연결 끊김 시 자동 폴드 처리, 세션 내 게임 한정
4. **허용 베팅 액션** (폴드·체크·콜·레이즈·올인만) 확정 — 하우스룰 미지원
5. **구현 우선순위**: 룰 엔진 → WebSocket 서버 → HTML5 클라이언트 순서로 진행하는 것에 동의 요청

승인 후 Phase 1 (범위 정의) 단계를 병렬로 시작한다.
