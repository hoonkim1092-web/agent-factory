## 설계 의도
- `Game Logic Dev` 역할이 담당하는 핵심 규칙과 상태 전이의 경계를 명확히 고정한다.
- 다른 역할이 제공해야 하는 입력 계약과 `Game Logic Dev`가 반환해야 하는 출력 계약을 문서화한다.
- 이후 `build` 단계에서 구현 순서가 흔들리지 않도록 선행 의존성과 산출물을 고정한다.

- `docs/change_history.md`

## 제안 변경
### 1. 구현 범위 고정
- 입력으로 전달된 최근 회차 이력, 통계 요약, 추천 설정을 검증한다.
- 추천 후보 생성에 필요한 규칙 평가 순서를 고정한다.
- 후보 번호 조합의 상태를 `초기화 -> 생성 -> 규칙 검증 -> 점수화 -> 정렬 -> 최종 선택`으로 관리한다.
- 추천 결과에 포함될 메타데이터 구조를 고정한다.

### 2. 인터페이스 계약 고정
- 입력 인터페이스: 회차 이력 목록, 통계 요약 객체, 추천 설정 객체.
- 출력 인터페이스: 추천 조합 목록, 규칙 적용 로그 요약, 실패 사유 목록.
- 오류 계약: 필수 입력 누락, 범위 밖 숫자, 후보 부족, 규칙 충돌을 명시적 오류로 반환한다.

### 3. 구현 순서 고정
1. 도메인 타입과 상태 모델 정의
2. 입력 검증 규칙 구현
3. 후보 생성 및 필터 규칙 구현
4. 점수화 및 정렬 규칙 구현
5. 결과 직렬화 계약과 handoff 포맷 정의

## 대안 검토
### 대안 A. 규칙과 상태 전이를 한 함수에 통합
- 장점: 초기 구현이 빠르다.
- 단점: 검증과 회귀 테스트 경계가 흐려져 후속 변경 비용이 커진다.
- 결론: 채택하지 않음.

### 대안 B. 상태 전이와 규칙 평가를 분리
- 장점: 입력 검증, 후보 필터, 점수화를 독립적으로 검증할 수 있다.
- 단점: 초기 문서화 항목이 다소 늘어난다.
- 결론: 채택.

## 검토 요청 메모

- 도구가 제공되는 즉시 본 문서를 기준으로 교차검증 요청을 보내야 한다.
