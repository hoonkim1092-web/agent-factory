## 설계 의도
- 동행복권 회차 원본을 **로컬 SQLite 캐시**에 유지하면서, 상위 소비자(통계 분석 엔진·추천기·리포트)에게 안정적인 읽기 인터페이스를 제공한다.
- Backend Dev `LottoStorage`(저수준 CRUD)와 Frontend Dev `LottoCollector`(증분 수집 오케스트레이션) 위에 **캐시 정책 계층**을 얹어 다음 책임만 담당한다.
  - "읽어도 되는가?"(신선도·최소 회차 수 판정)
  - "부족하면 수집하라"(수집기 위임 호출과 결과 요약)
  - "정합성은 깨지지 않았는가?"(연속 회차 검증, 누락 구간 탐지)
- 상위 소비자가 매번 `LottoStorage.get_draws`와 `LottoCollector.sync_incremental`을 직접 호출해 중복 로직을 구성하지 않도록, 도메인에 특화된 읽기 API(최근 N개, 전체 목록, 단일 회차, 상태 요약)를 한 곳으로 모은다.
- 구현 순서를 파일 단위로 미리 고정해 build 단계에서 책임 경계가 흔들리지 않게 한다.

## 역할 경계 (다른 모듈과의 분리)
- Backend Dev `LottoStorage`의 책임
  - SQLite 연결 수명, DDL 적용, 트랜잭션 경계.
  - `upsert_draws`, `get_draws`, `get_draw`, `get_checkpoint`, `set_checkpoint` 등 저수준 CRUD.
  - 도메인 타입(`LottoDraw`, `FetchCheckpoint`)의 직렬화·역직렬화.
- Frontend Dev `LottoCollector`(module_1)의 책임
  - 체크포인트 기반 증분 수집 루프, 최신 회차 탐색, 부분 성공 집계(`SyncResult`).
  - 호출 간 rate limit, 연속 실패 중단 정책.
- Frontend Dev 캐시 저장소(`frontend_dev_module_2`)의 책임
  - 도메인 수준 신선도 판정(보유 회차 수, 최신 회차와 오늘 날짜 비교).
  - 부족/만료 시 `LottoCollector.sync_incremental`을 위임 호출하고 결과를 요약.
  - 도메인 읽기 API(`get_recent_draws`, `get_all_draws`, `get_draw`) 노출.
  - 회차 연속성 검증(`validate_continuity`)과 누락 구간 리포트.
  - 읽기 전용 모드(`offline=True`)에서 수집 호출을 생략하는 모드 제공.

## 모듈 범위
### 포함
- 캐시 상태 요약: 보유 회차 수, 최신 회차, 마지막 수집 시각, 신선도 플래그.
- 신선도 판정 정책: `required_draws`(최소 보유 회차 수), `freshness_hours`(체크포인트 유효 기간).
- 캐시 준비(`ensure_ready`) 플로우: 상태 조회 → 필요 시 `sync_incremental` 호출 → 결과를 캐시 상태에 병합.
- 도메인 읽기 API: 최근 N개, 전체, 단일 회차. 모두 `LottoDraw` 튜플 형태로 반환.
- 연속성 검증: `[min_no..max_no]` 범위에서 누락 회차 목록을 보고하는 `validate_continuity`.
- 읽기 전용 모드: 네트워크가 없는 환경에서도 저장된 데이터만으로 동작하도록 보장.

### 제외
- SQLite 연결 관리, DDL, 트랜잭션(= Backend Dev).
- 단일 회차 HTTP 호출과 재시도(= Backend Dev).
- 증분 수집 루프·rate limit(= Frontend Dev 수집기 module_1).
- 통계 계산, 추천 번호 생성, 리포트 출력(= 상위 모듈).
- 번호 규칙 검증(= Game Logic Dev).
- GUI, 웹 서버, 결제/구매 연동.

## 공개 인터페이스 (계약 초안)
### 설정
```text
CacheConfig(
    required_draws: int = 500,
    freshness_hours: float = 24.0,
    refresh_policy: Literal["auto", "never"] = "auto",
    offline: bool = False,
)
```
- `required_draws`: 최소 보유 회차 수. 부족하면 `stale=True`.
- `freshness_hours`: 체크포인트가 이 시간 이상 경과했으면 `stale=True`.
- `refresh_policy="never"` 또는 `offline=True`: `ensure_ready`에서 수집 호출을 생략하고 현재 상태만 반환.

### 데이터 객체
- `CacheStatus`
  - `total_draws: int`
  - `latest_drw_no: int | None`
  - `earliest_drw_no: int | None`
  - `last_fetched_at: datetime | None`
  - `is_stale: bool`
  - `stale_reasons: list[Literal["missing_checkpoint", "insufficient_draws", "expired_checkpoint", "unknown"]]`
- `CacheReadyResult`
  - `status: CacheStatus`
  - `sync_result: SyncResult | None` — 실제 수집을 수행한 경우만 채움.
  - `action: Literal["skipped", "synced", "offline"]`
- `CacheGapReport`
  - `expected_range: tuple[int, int] | None`
  - `missing_draws: list[int]`
  - `is_continuous: bool`

### 클래스
```text
LottoDrawCache(
    storage: LottoStorage,
    collector: LottoCollector | None = None,
    config: CacheConfig = CacheConfig(),
    clock: Callable[[], datetime] = datetime.now,
    logger: Logger | None = None,
)
  .status() -> CacheStatus
  .ensure_ready() -> CacheReadyResult
  .get_recent_draws(n: int) -> list[LottoDraw]
  .get_all_draws() -> list[LottoDraw]
  .get_draw(draw_no: int) -> LottoDraw | None
  .validate_continuity() -> CacheGapReport
```

### 외부 입력
- Backend Dev `LottoStorage`(의존성 주입). 캐시는 저장소 연결 수명을 직접 관리하지 않는다.
- Frontend Dev `LottoCollector`(선택적 주입). 주입되지 않거나 `offline=True`면 수집을 건너뛴다.
- `clock`: 테스트에서 고정 시간 주입이 가능하도록 현재 시각 함수를 외부에서 받는다.

### 외부 출력
- 메서드 반환값(`CacheStatus`, `CacheReadyResult`, `list[LottoDraw]`, `CacheGapReport`).
- 부수효과: 수집 호출 시 `LottoCollector.sync_incremental()`을 통해 `LottoStorage.upsert_draws`/`set_checkpoint`가 발생(캐시 자체는 추가 SQL을 발행하지 않는다).

## 에러 및 장애 시나리오
- 저장소가 비어 있음(체크포인트 없음)
  - `CacheStatus.is_stale=True`, `stale_reasons=["missing_checkpoint", "insufficient_draws"]`.
  - `ensure_ready`는 `collector`가 있으면 `sync_incremental` 호출, 없거나 `offline=True`면 `action="offline"`.
- 보유 회차가 `required_draws` 미만
  - `stale_reasons`에 `"insufficient_draws"` 포함. `ensure_ready`가 수집 호출로 보충 시도.
- 체크포인트가 `freshness_hours`를 초과해 오래됨
  - `stale_reasons`에 `"expired_checkpoint"` 포함. 정책에 따라 수집 또는 skip.
- 수집 호출 중 `SyncResult.stopped_reason="aborted"`
  - `ensure_ready`는 예외를 올리지 않고 `CacheReadyResult.sync_result`에 그대로 보존. 호출자가 로그·재시도 결정.
- `validate_continuity`에서 누락 구간 발견
  - `is_continuous=False`, `missing_draws`에 회차 번호 리스트 포함. 호출자가 `LottoCollector.sync_range`로 백필 결정.
- `get_recent_draws(n)` 호출 시 `n<=0`
  - `ValueError` 발생(도메인 의도와 어긋나는 호출은 조기 차단).
- 저장소 예외는 캐시에서 잡지 않고 호출자에게 전파(Backend Dev 계층 책임 경계 유지).

## 비기능 제약
- 기본값: `required_draws=500`(프로젝트 목표치 기준), `freshness_hours=24.0`, `refresh_policy="auto"`, `offline=False`.
- 캐시 계층은 SQL을 직접 발행하지 않고 항상 `LottoStorage` 공개 메서드를 통한다.
- 로그는 주입 가능한 `logging.Logger`. 기본 로거는 `lotto_predictor.cache`.
- 모든 새 주석·로그·오류 메시지는 한국어로 작성한다.
- 도메인 타입(`LottoDraw`) 반환값은 항상 오름차순 보장(Backend Dev 계약 재사용).

## 대안 검토
- 대안 1: 캐시 계층이 자체 SQLite 테이블을 추가한다.
  - 기각: Backend Dev 스키마와 이중 관리되고 트랜잭션 경계가 흐려진다.
- 대안 2: 캐시가 `LottoCollector`를 내부에서 생성한다.
  - 기각: HTTP 클라이언트 생성 책임이 캐시로 번지고 테스트 주입이 어려워진다.
- 대안 3: 메모리 LRU 기반 캐시.
  - 기각: 요구사항은 500회차 이상 장기 보관. SQLite 영속이 적합.
- 대안 4: 읽기 전용 모드를 별도 클래스로 분리.
  - 기각: `CacheConfig.offline` 플래그로 충분. 클래스 분리는 과도한 설계.
