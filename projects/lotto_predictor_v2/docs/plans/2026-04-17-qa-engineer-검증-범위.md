## 메타데이터
- 작성일: 2026-04-17
- 관련 task_id: `qa_engineer_module_10_scope_1`
- 상태: review_pending

## 설계 의도
- QA Engineer가 구현 단계에서 바로 사용할 수 있는 검증 범위와 입력 인터페이스를 고정한다.
- 다른 역할의 산출물을 어떤 순서로 검증할지 선행 의존성을 문서화한다.
- 검증 산출물의 최소 형태를 고정해 이후 verify 단계의 handoff 기준을 명확히 한다.

## 영향 범위
- `docs/architecture.md`: QA 검증 워크플로와 인터페이스 정의 추가
- `docs/task_execution_plan.md`: QA Engineer 단계의 의존성, 산출물, 구현 순서 상세화
- `docs/change_history.md`: 본 설계 변경 이력 추가

## 검증 범위
- 데이터 수집 플로우 검증: 최신 회차까지 증분 수집, 실패 시 재시도 또는 캐시 fallback
- 분석 플로우 검증: 최근 500회차 기준 통계 계산 결과의 형식과 핵심 수치 일관성
- 추천 플로우 검증: 동일 `seed` 입력 시 동일 조합 재생성, 조합 개수와 숫자 범위 준수
- 출력 플로우 검증: 터미널 리포트 필수 섹션과 근거 지표 노출 여부
- 배포 플로우 검증: PyInstaller 실행 산출물 존재와 기본 실행 가능 여부
- 문서 플로우 검증: 사용자 실행 가이드가 실제 실행 절차와 일치하는지 확인

## QA 인터페이스
- 입력:
  - Backend Dev 검증 대상 산출물 경로 또는 모듈 진입점
  - Frontend Dev 산출물: 수집기, 캐시, 분석, 추천, 리포트, 빌드 스펙, 사용자 가이드
  - Game Logic Dev 산출물: 규칙/상태 전이 계약 또는 관련 테스트 진입점
  - 재현 파라미터: `seed`, 기준 회차 범위, 기대 산출물 경로
- 출력:
  - 검증 실행 기록
  - 실패/회귀 시나리오 목록
  - `verification-report.md` 형태의 최종 검증 결과 문서
  - 다음 작업자를 위한 handoff 메모

## 구현 순서
1. 검증 대상 인터페이스와 경로를 확정한다.
2. 핵심 플로우 smoke 시나리오를 작성한다.
3. 회귀 시나리오와 실패 시나리오를 작성한다.
4. 산출물 점검표와 결과 문서 템플릿을 작성한다.
5. verify 단계에서 최종 실행 결과와 잔여 리스크를 기록한다.

## 대안 검토
- 대안 1: 역할별 검증 범위를 각 모듈 문서에 분산 기록
  - 기각 이유: QA 단계의 전체 순서와 교차 의존성이 흐려진다.
- 대안 2: QA 단계에서만 산출물 형식을 정한다.
  - 기각 이유: build 단계에서 필요한 인터페이스가 늦게 확정되어 재작업 위험이 커진다.

## 검토 요청 메모
- 현재 실행 환경에는 `read_mailbox`, `send_mailbox_message`, `ack_mailbox_message` 도구가 노출되어 있지 않아 문서 작성까지만 선행한다.
- 교차검증 요청은 도구가 제공되는 런타임에서 `review_request` 메시지로 이어서 수행해야 한다.
